# Shared template acceptance and runtime rehearsal

This reference distinguishes the creator's reusable publishing verification from each plumber's actual website launch. Record the exact source and observed outcomes. No result is already passed merely because this file is included.

## 1. Shared source and GitHub workflows

Publish the reviewed neutral tree to the business-owned template repository. Verify the complete file contents, template flag, default branch and recorded commit. Create an isolated private copy with an authorized account and run the included validation workflow.

Exercise the phone import with a known-good production fixture: `website.zip` must produce a validated normal-file commit under `public/`. Exercise a representative rejected package and confirm the previous tree is preserved. The local hostile/size matrices cover the full rejection set; do not repeat every large hostile fixture remotely unless a changed workflow or failure warrants it. Exercise history-preserving GitHub public-tree rollback against known-good disposable source.

A separate ordinary account is useful access coverage when available. Record the account context actually used; do not claim a separate-account test from the creator's account.

## 2. Required acceptance for the normal Git-to-Pages route

Connect the disposable repository through **Cloudflare Pages Git integration** with no framework, repository root, blank build command, `public` output and `main`. Record any tested `exit 0` exception when an existing project refuses a blank command.

Verify static pages and actual `/api/health` JSON at the HTTPS `pages.dev` address, including expected headers and preview indexing. A harmless `main` commit must cause an automatic deployment whose source commit matches GitHub. Check the deployable result and a Cloudflare deployment restore. Retain known-good source and recovery evidence.

The template's advertised Git integration is accepted only after this route is observed. Publication alone or a local pass cannot establish it. If authorization blocks this route, identify that blocker and keep this acceptance item open.

## 3. Separate compiled runtime rehearsal

A correctly compiled API/Wrangler deployment of the reviewed source is meaningful evidence of the deployed static files, Functions, security responses and any exercised rollback. Record the compiled artifact/source identity, deployment method, environment and checks. Verify the expected JSON and status from `/api/health`; an HTML fallback or generic HTTP 200 is insufficient.

This runtime result does **not** verify the Cloudflare GitHub app, repository access, automatic builds from `main`, or the complete phone upload → Git commit → Pages chain. Keep it separate from section 2.

Dashboard drag-and-drop does not compile the repository's `functions/` folder. Cloudflare supports a prebuilt `_worker.js` artifact, but uploading raw Functions files does not create that artifact. A Direct Upload project cannot be converted into Git integration; use a new Git-connected project when needed. [Cloudflare Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/), [Functions deployment](https://developers.cloudflare.com/pages/functions/get-started/).

## 4. Customer program and artifact checks

Check the exact delivered desktop folder, phone source and copy-ready guide prompts. The phone path starts in a Work-capable Project; starting outside and moving into the Project is a fallback only when Work is unavailable there.

Use fictitious plumbing facts to check homepage-only concept, a meaningfully different Randomize option, full build after concept approval, exact finished-site review and explicit final launch approval. Reuse sufficient setup authorization and do not repeat approval for the same hosted version. Check Business Asset Package delivery or decline; accepted files use only the customer's brand and 2–4 relevant plumbing extras.

Record actual device/account coverage. Missing physical-phone access is an unrun interaction check, not a fabricated failure. Verify the selected storefront's customer download path if a storefront has been configured; no store is mandatory for this template.

## 5. Checks that belong to each real website

Before that plumber's launch, verify approved facts, public content/privacy, mobile and accessible interactions, the actual phone/contact destination, and final owner approval. Enable an on-site form only after configuring and testing the actual recipient, origins and Turnstile; otherwise retain a verified contact route.

Apply custom-domain HTTPS, canonical/redirect, existing DNS/email and old-URL preservation checks to the actual domain being changed. Verify restricted preview access if confidentiality is required. Record the customer's recovery point and monitoring only when configured. A blank shared template has none of these customer's business resources to migrate.

## Evidence labels

Use **passed locally**, **passed live**, **failed**, **blocked by access**, **not run**, or **not applicable**, with the relevant source/deployment and reason. A compiled runtime pass can coexist with Git integration still blocked. Do not collapse unrelated customer or optional distribution checks into a blanket all-fields-must-pass release rule. Never record secrets or actual customer inquiries in evidence.
